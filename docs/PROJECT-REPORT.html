1. What it is, in one page

Argus is a Windows desktop application that watches what a single program actually does while it runs, and tells you how suspicious that behaviour is — with the reason, and with what it could not see.

You start Argus, choose an executable (say notepad.exe or a file you downloaded), and Argus captures the operating system's own event stream for that process and every process it creates: process starts, file writes, registry writes, network connections, DNS lookups. Those raw events are normalised, attributed to the program's process tree, fed to 23 named detection rules, merged into detections, and turned into one 0–100 risk score. A browser dashboard shows it live, and you can export a self-contained HTML report.

The idea is dynamic analysis: you do not read the binary's bytes (that is static analysis) — you observe what it does. And the distinguishing engineering choice of this project is that every claim carries its own limits:

Three design commitments that shape every file in the repo

  1. Every detection explains itself. A finding is not a title, it is a RuleFinding with a Reason ("reg.exe wrote an autostart value under CurrentVersion\Run, which Windows runs at sign-in") and a Counterfactual ("would not fire for a read or a delete, or for a key Windows does not execute"). If the rule cannot explain itself, it does not ship.
  2. Evidence is labelled by how directly it was seen. Every event carries Observability = Direct / Partial / Inferred / Aggregated, and the UI renders it. Reading and writing evidence are never blurred together.
  3. Absence of evidence is reported as such. If the sensor dropped events, the session says "incomplete" with the reason. "No detections" is phrased as "no significant observed indicators", never "safe".

2. Why it exists (the problem)

Antivirus asks "is this file known-bad?" It fails against anything new. The professional answer is to run unknown software in a sandbox and watch it. That is what tools like Cuckoo or Process Monitor do, and each is awkward: Procmon gives you thousands of raw events with no judgement at all; a full sandbox needs a second machine and heavy tooling.

Argus takes a middle position: one machine, one program, real operating-system telemetry, and a judgement that is explainable line by line. It is deliberately not a sandbox (it does not contain the program), not an antivirus (no signatures, no blocking), and not a service (it only sees what happens while a session is open). Those three negatives are stated in the docs and are better said in the viva than discovered by the examiner.

ApproachWhat you getWhat it costs
Static analysis / antivirusFast, works on files at restBlind to what the program actually does; new malware is invisible
Full sandbox (Cuckoo)Containment, network simulationSecond machine, heavy setup, hard to do live
Procmon / raw ETWComplete truth, no interpretationToo much data; no judgement, no explanation
ArgusLive behavioural judgement with reasons, counterfactuals and stated blind spotsNo containment; single session; sees only the monitored tree

The shape is a pipeline with one narrow data contract in the middle. Everything upstream of BehaviorEvent is Windows-specific and untestable off Windows; everything downstream is pure logic and fully unit-testable on any machine. 6. Trace one event end-to-end

This is the single most useful thing to be able to narrate. Pick "reg add ...CurrentVersion\Run" and tell the story:

  1. The operator launches the target from the dashboard ("Monitor an application"). The agent checks the file exists and is an executable, then SessionManager.StartAsync opens a SQLite database and a JSONL recorder, and starts ETW before the target process is created (late root attach), so the first ~150 ms is not lost.
  2. The kernel fires events. The target starts reg.exe — Windows raises a ProcessStart record. When reg.exe writes the value, the kernel registry provider raises a registry write record carrying the kernel object for the key.
  3. EtwEventMapper normalises the raw record into a BehaviorEvent: kind, pid, target, timestamps, Observability. For the registry write, the key name comes from the earlier open record, joined through the kernel object pointer — hence Inferred.
  4. The scope tracker decides whether the event belongs to the monitored tree (Observe(event) → Root/Confirmed/Unconfirmed/Excluded). Out-of-scope events are counted but not reasoned about.
  5. The event is stored (SQLite row + JSONL line) so the report can later cite its exact evidence by sequence number.
  6. The pipeline runs the rules. Each IEventRule.Evaluate(context) returns zero or more RuleFinding. AutostartKeyRule matches a value write under ...\CurrentVersion\Run and returns a finding with its reason and counterfactual.
  7. The aggregator merges it into a DetectionState keyed by rule+process. Repeated hits raise the count and confidence; a second evidence channel escalates the card.
  8. The scorer recomputes 0–100 from severity, confidence, age-decay and corroboration and picks the band. An SSE state frame reaches the dashboard and the Live screen re-renders.
  9. At the end the report is rendered from one SessionReport.Snapshot: verdict, score, counts, detections with their evidence, gaps, observability table and config digest — as HTML and as JSON.
kernel ETW --> EtwEventMapper --> BehaviorEvent --> scope? --> store (SQLite + JSONL)
                                                 |
                                                 v
                                23 rules -> RuleFinding -> aggregator -> DetectionState
                                                 |
                                                 v
                                 RiskScorer (0-100) -> band -> SSE -> dashboard / report

7. Scope tracking: what gets watched

Argus does not report the whole machine; it watches one process tree. The ProcessScopeTracker answers "is this event part of the story?" as a state machine over parent links, not a list of PIDs.

  • Root — the launched target.
  • Confirmed — a process whose parent was observed inside the tree.
  • Unconfirmed — attributed by location (started from the root's directory) or because its parent chain was never recorded.
  • Excluded / OutOfScope — everything else, including the agent's own ancestors.

The interesting, honest case is Unconfirmed. Real payloads often escape their recorded parent chain (a short-lived cmd.exe spawns something and dies before the table records it). The tracker then attributes by location — weaker evidence — and the event carries Unconfirmed so nothing downstream can mistake it for a confirmed child. P-008 exists to read exactly this: a process in the application's directory with no observed creator is the process-table footprint of cross-process creation, which the kernel provider used here cannot see directly.

Exclusions are measured, not guessed. Four examples, each found by running real software:

  • P-004 ignores the monitored root and the root's own directory — a per-user install such as %LOCALAPPDATA%\Programs\Python\python.exe is where the operator installed it.
  • P-006 ignores a launch whose image equals its parent's image — a browser's own --type=... children are not "the same program re-launched with different switches".
  • F-007 excludes compiler caches — the C# compiler's analyzer cache was reported as a dropped payload.
  • F-007 also excludes the PowerShell scratch directory, after a probe tripped it.

8. The 23 rules, explained

Rules are named F- (file), N- (network), P- (process) and X- (correlated). Each has a severity, a channel, a MITRE ATT&CK tag and a kind: per-event (one event) or aggregated (a pattern over a window). In the viva, know why each rule exists and one sentence on how it avoids false positives — that is what shows you built it.

Every rule ships with at least one firing fixture and one quiet twin. That pair is the definition of "the rule works": it fires when the behaviour is present and stays quiet when it is not.

9. The scoring model (with maths)

The score answers "how much does the evidence so far warrant attention?" It is not a probability of malware and it is not additive — that is the part examiners probe. The code is src/Argus.Core/Risk/RiskScorer.cs.

Step 1 — each detection becomes a weight

weight = severity/100  ×  confidence  ×  decay(age)

decay(age) = max(0.60, 0.5 ^ (age / 15 min)) — evidence fades with a 15-minute half-life but never below 0.60 while the session is open. Old evidence matters less; it is never forgotten mid-session.

Step 2 — combine as independent evidence, never as a sum

base    = 1 - Π (1 - weight_i)          // "noisy-OR": the chance that at least one is real
indep.  = number of distinct evidence categories present (file / registry / network / process…)
corroboration = min(1.25, 1 + 0.08 × (independent - 1))
score   = clamp(round(base × corroboration × 100, 1), 0, 100)

Why noisy-OR instead of a sum: adding severities lets three weak, related findings reach 100 and scream "malicious", and the total could exceed any meaningful ceiling. Combining as independent evidence means ten copies of the same weak signal asymptote towards it rather than stacking past it. The corroboration factor then rewards findings on different channels — persistence in the registry plus a network callback in the same session is genuinely more convincing than two file writes.

Step 3 — decide the band

ConditionBandExplanation printed with it
score ≥ 65 and ≥ 2 independent categories (or a critical rule: severity ≥ 90 at confidence ≥ 0.80)Malicious"Risk X is at or above the malicious threshold, corroborated by N independent evidence categories"
score ≥ 65 but only one category and no critical ruleSuspicious"Risk X exceeds the malicious threshold, but only one evidence category is represented, so the verdict stays suspicious"
score ≥ 20, or a single rule at severity ≥ 45 firedSuspicious"Requires investigation: risk is between the two thresholds / a single high-severity rule fired without corroboration"
otherwiseBenign"Below the suspicious threshold. No significant indicators were observed; that is not proof of safety."

That second row is the most defensible line in the project: a high score from a single channel is deliberately not called malicious. One suspicious behaviour is a lead; two independent ones are a story. You can also point at the third row: a severity-45 rule fires suspicious on its own, so a clear single-behaviour problem is never buried under the arithmetic.

The thresholds live in RiskOptions (suspicious 20, malicious 65, critical 90/0.80, half-life 15 min, floor 0.60, corroboration step 0.08 capped at 1.25) — data, not constants, and the model is unit-tested against hand-computed values.

10. Honesty rules: observability, gaps, signatures

This section is the intellectual core of the project, and the most likely place for a hard viva question. Each item below is a rule the code enforces, not a slogan in the README.

(a) Observability is a field, not an adjective

Every event carries a level, and the dashboard renders it on every row:

LevelMeansExample
DirectCaptured from an OS event for this process.Process creation, file write, TCP connect.
PartialCaptured, but attribution or completeness is limited.A read sampled under volume pressure; a process-start whose image path could not be resolved.
InferredDeduced from a heuristic instead of observed.Injection indicators; a registry write whose key was joined through a kernel object pointer.
AggregatedA rollup of many events; raw detail has aged out.Summarised burst counts.

(b) Gaps and coverage: "absent" is not "did not happen"

If the sensor loses events, the session stops calling itself complete. CoverageAssessment turns loss counters into CoverageDto { Complete, Gaps, Reasons, Statement }, the dashboard shows a banner that cannot be dismissed, and the report derives a limitation sentence from the real gap list: gaps present → "anything inside them may be missing"; no gaps → "the sensor believes it delivered every event it produced". Two different sentences, because they are two different claims.

(c) Signatures are three-way, and two obvious methods were wrong

SignatureStatus is Valid / Invalid / Unknown, and no value is never read as "unsigned". Two plausible implementations were measured and rejected before the current one:

  • X509Certificate.CreateFromSignedFile reads only an embedded certificate. Most of System32 has none — Windows verifies those by hashing the file and looking the hash up in a signed catalog. That API called a copy of whoami.exe unsigned while Get-AuthenticodeSignature said Valid, Catalog, Microsoft Windows. That is a false fact about provenance, not a threshold to tune.
  • WinVerifyTrust resolves embedded signatures only and returns TRUST_E_NOSIGNATURE (0x800B0100) for a catalog-signed file — byte for byte the same code as a file with no signature at all.

The shipped path builds the Authenticode chain explicitly and treats "could not determine" as Unknown, which is why P-005 stays quiet instead of guessing.

(d) A failure message must tell the truth about the machine

When the window cannot show the dashboard, the message must not claim "nothing is being monitored" while the agent is running. It prints what failed, and the working dashboard URL. Similarly: unknown counters render as "—", never 0, so a broken stats frame and a quiet sensor cannot look alike.

(e) Weaker evidence is labelled, never presented as stronger

Three cases you can quote: a registry write joined through a kernel object pointer is Inferred (and dropped as soon as the kernel retires the object, because pointers are reused — the same value was measured belonging to two unrelated keys). A process attributed by location is Unconfirmed in scope. A read that was sampled says so in the counters. In each case the rule that consumes the evidence is written to survive the weaker reading.

11. Sensors: ETW, polling, and what they cannot see

ETW in one minute

Event Tracing for Windows is the kernel's own event bus. A session subscribes to providers with keywords naming categories of events, and events are delivered to a callback in user space. Argus opens its own session (named Argus-<random>) and uses the kernel provider's process/file/network keywords plus the DNS client provider and the kernel registry manifest provider.

Two things worth knowing because they came up in the work:

  • Why not the NT Kernel Logger? That session is exclusive — one at a time — so it collides with Procmon and Sysmon. Argus uses manifest providers in its own session instead.
  • Session leak. Killing an agent leaves its ETW session registered, and the session table is a machine-wide limited resource. Six dead sessions made the next launch fail with 0x800705AA "Insufficient system resources", which reads as memory pressure and is nothing of the kind. EtwCollector.ReclaimStaleSessions() stops only Argus-* sessions at startup and reports what it reclaimed; EtwStartFailure.Explain turns the two named HRESULTs into sentences with the fix.

Why polling is still needed

Kernel events are complete for process creation but thin on metadata: the image path of a short-lived process and the owning process of a TCP connection are frequently unavailable at event time. So there are two pollers — a process snapshot (to back-fill metadata) and the TCP table (to attribute connections). Polling results are marked Source = Polling, never confused with Etw.

What the sensor cannot see (say this before he asks)

Two design decisions you will be asked about

1. The agent serves the dashboard instead of a proxy. Same origin means the bearer token and the host/origin guard work with no CORS and no Origin rewriting. An earlier proxy setup produced exactly the bugs the switch removed: a rewritten Host header and a 403 on the ticket POST.

2. SSE uses single-use tickets, not a token in the URL. EventSource cannot send an Authorization header, so the usual shortcut is ?token=... — which then lives in the address bar, the browser history and any proxy log. Instead the client POSTs to /api/sessions/{id}/stream-ticket with the bearer header and receives a ticket valid for 30 seconds and one use. Scripts: check-stream-ticket.sh (8/8) and check-sse-reconnect.sh (4/4, reconnects and recovers the snapshot).

The desktop shell (Argus.Desktop)

WinForms + WebView2, running at normal integrity (asInvoker). It starts argus-agent --elevate, waits for the agent's ready line (JSON with port and token), then shows the dashboard inside a WebView2 control. Its own bugs were found by running it, and they are good viva material:

  • Deadlock on ReadToEnd. The elevated child inherits the pipe handle, so the parent blocked waiting for EOF that could never come. Fixed by reading until the first {-prefixed line, bounded to 90 s.
  • async void swallowed failures. Exceptions in an async void method are not awaited, so the window failed silently. Now caught, written to %TEMP%\argus-desktop.log with exception.ToString(), and surfaced in the window.
  • WebView2Loader.dll missing from output, producing a bare E_NOTIMPL (0x80070032) that names neither the file nor the architecture. Copied explicitly by the project file.
  • The runtime locator read only the machine-wide registration. The runtime was installed per user; the check said "not installed". It now reads HKLM (native + WOW6432Node) and HKCU and uses the registration's own location. Measured: WebView2 runtime 157.0.4341.42 (per user), and the eight-screen dashboard rendered in the window.

13. The report export and Settings

Report export

The report exists in two formats rendered from one snapshot (SessionReport.Snapshot), so a section cannot appear in one and be missing from the other — two independent builders had already begun to drift.

  • HTML: executive summary (target, verdict + score + peak, window, coverage), activity counts, every detection with reason, counterfactual, categories, timestamps and its own evidence events with observability, the process table with signatures, risk over time, collection health, the observability table, limitations, and the raw JSON bundle embedded in the document. No scripts, no external asset — a live test asserts that a report cannot need the network to render.
  • JSON: the same data for tooling.
  • Limitations are derived, not boilerplate: a report that prints the same five caveats every time trains the reader to skip them. Gaps present → "anything inside them may be missing"; the volume fuse throttled → "the counts are a sample under pressure"; counters unreadable → a different warning again.
  • Provenance: agent version, Windows build and a configHash (SHA-256 over the rule thresholds + version, 16 hex). Two sessions recorded under different thresholds are not comparable, and the report says which one produced it.
  • Downloading it had to be a fetch. A link cannot carry the bearer header and a token in a URL is exactly what the tickets avoid, so the button fetches with the header, turns the response into a blob and saves it. The token never reaches the address bar, history or a proxy log.

Settings reports rather than pretends

The plan sketched a page of toggles (collection profile, sampling, retention, ML mode). The agent parses its options at launch and loads the rule settings once — nothing reloads — so a toggle could not take effect. Instead GET /api/settings (read-only) answers what is in force: version, pid, elevation, OS build, runtime, the bound port, data root, dashboard root, ETW session name, duration limit, every rule threshold with its human label and its raw key, the config digest and the observability table. The screen prints them with the restart instruction beside them, carries no checkbox or slider, and a test asserts that.

Writing it exposed a small lie: --port 0 (let the OS choose) was reported as port: 0. The endpoint now reports the port Kestrel actually bound and keeps the requested one beside it.

14. Testing: how I know it works

The fixture harness (why the 54 scenarios are the real evidence)

A scenario is a .jsonl file: a $meta line declaring expectations, then recorded events. Argus.Cli replays them through the real pipeline (same normalizer, same scope tracker, same rules, same scorer) and asserts the outcome.

{"$meta":{"name":"unsigned-setup-spawns-shell",
  "expect":{"rules":["P-002"],"absentRules":["P-001"],"band":"Suspicious",
            "minScore":10,"maxScore":35,"maxDetections":2}}}

Each rule needs at least one firing fixture and one quiet twin. That is what makes "the rule works" a measurement rather than an opinion, and the absentRules field is what caught P-001 and P-002 double-firing on every shell scenario.

The benign corpus (docs/BENIGN-CORPUS.md)

Six real applications — notepad, 7-Zip, Python, dotnet run, Chrome, an Electron IDE — captured live and expected to produce Benign 0.0, zero detections, zero gaps. This is the false-positive test, and it is where three rule bugs were found on evidence (§15).

The gates

bash scripts/verify.sh          # build, all tests, catalogue gate, all 54 scenarios, self-test, load
powershell scripts/verify.ps1 -Smoke   # the Windows live smoke (needs elevation)

The catalogue gate is worth mentioning: docs/RULES.md must match argus rules --markdown exactly, so a rule cannot be added or re-severitied without its documentation changing in the same commit.

The dashboard tests

Playwright runs against payloads captured from real sessions by scripts/dashboard-fixtures.ps1 (two sets: benign and flagged), not against hand-written mocks — so a DTO change cannot pass the test while breaking the UI. Two modes on one code path: ?fixtures= or live + bearer. The live suite additionally covers the launch flow, the ticket stream, the stats frame and the export download.

16. Limitations — say these before he asks

Product limitations (by design, not defects)

  1. Not a sandbox. Argus observes; it does not contain, block or clean. Running a real sample on your own machine is still dangerous.
  2. Not a service. Nothing is collected before a session starts or after it stops, and a session list is per agent process — restarting the agent does not show old sessions in the UI (the SQLite databases are still on disk under %LOCALAPPDATA%\Argus\sessions).
  3. One monitored tree. Machine-wide activity outside the root's tree is counted as "outside scope", not analysed.
  4. Rule-based, not learning. 23 hand-written rules with tunable thresholds. No model. A machine-learning advisory layer is the next phase in the plan and has not been built.
  5. Near-real-time. ETW buffering and batching add roughly 1–3 seconds; nothing here is hard real-time.

Unverified on this machine (say it plainly)

  • The UAC consent click itself (an unattended VM cannot press Yes); the relaunch path is code, not observed end to end.
  • Event loss and the volume fuse under sustained heavy load on a busy machine.
  • A non-trivial target such as 7-Zip end to end through the dashboard (it is in the benign corpus, but the full launch → report path was driven with simpler targets).

Why say this: the project's own thesis is that a tool must state what it did not see. Reading the limitations out before the examiner finds them is consistent with the work and removes the only argument that could damage the viva.

17. Viva questions and answers

Grouped the way a 30-minute viva arrives: opening questions, then "how does it actually work" (random pokes), then code-level questions, then the harder design questions. Each answer is written to be said out loud in about 20–40 seconds.

A. Opening / what and why

What does your project do, in one sentence?
It watches a single Windows program while it runs — process starts, file writes, registry writes, network connections, DNS — and gives it a 0-to-100 risk score with the reason for every finding and an explicit statement of what it could not see.
Lead with "single program" and "with the reason"; those are what make it different from Procmon.
How is this different from antivirus?
Antivirus asks "is this file known-bad" and needs a signature. Argus asks "what did this program do while I watched it" and reasons about behaviour, so it works on something nobody has seen before. It also does not block anything — it reports.
How is it different from Process Monitor?
Procmon shows raw events with no judgement. Argus filters to the monitored process tree, runs 23 detection rules, merges repeated hits, and produces a score with an explanation, a counterfactual and the evidence sequence numbers so you can jump back to the exact events.
What is the biggest limitation?
It is not a sandbox and it is not a service: it only sees what happens while a session is open, and it does not contain the program. I state that in the report itself, along with the specific things the sensor cannot see — for example file deletions made with del never appear as file events, which I measured: 26 deletions produced zero events.
Naming a measured gap is far stronger than "some limitations exist".

B. Random pokes: "how does X work?"

How do you get the events from Windows?
Event Tracing for Windows. I open my own ETW session and subscribe to the kernel provider for process, file and network events, plus the DNS client provider and the kernel registry provider. The agent is elevated because the kernel provider needs it. I deliberately do not use the NT Kernel Logger session, because it is exclusive and would collide with Procmon or Sysmon.
How do you know which process an event belongs to?
Two steps. The event carries the pid, and a scope tracker classifies it: the root target, a confirmed child whose parent I saw inside the tree, or unconfirmed — attributed by directory because its parent chain was never recorded. Everything else is out of scope and only counted. For TCP I read the TCP table because the connection event alone often cannot name the owner.
Show me a rule. Pick one at random.
Say it is N-002, beaconing. It does not count connections; it looks at the intervals between them and computes the coefficient of variation. A human browsing has irregular intervals; a beacon has nearly identical ones. If the variation is below the threshold with at least six connections in the window, it reports — grouped per endpoint, over ten minutes. It is "aggregated", not per-event, because no single connection is suspicious.
The two sentences that land: "it does not count, it measures regularity" and "per-event vs aggregated".
How do you avoid false positives?
Three ways. First, every rule has a quiet twin fixture, so a rule that fires on benign behaviour fails the test suite. Second, I captured a benign corpus of six real applications — notepad, 7-Zip, Python, dotnet run, Chrome, an Electron IDE — and the target is Benign 0.0 with zero detections and zero gaps; that exercise found three genuine rule bugs. Third, exclusions are narrow and named: P-004 skips the monitored program's own directory, P-006 ignores a child whose image equals its parent's, F-007 skips compiler caches.
What happens if the sensor drops events? Do you still say "clean"?
No. Coverage is computed from the loss counters; if events were lost the session is marked incomplete, the dashboard shows a banner that cannot be dismissed, and the report changes its limitation sentence to "anything that happened inside the gaps may be missing". And the benign verdict always reads "no significant observed indicators", never "safe".
What is the score exactly? Is it a probability?
No, it is a bounded evidence score, not a probability. Each detection becomes weight = severity × confidence × a time-decay factor with a 15-minute half-life and a floor of 0.6. The weights are combined with a noisy-OR — one minus the product of one minus each weight — so evidence cannot be summed past 100, and then multiplied by a corroboration factor of up to 1.25 when findings come from different channels. Bands: below 20 benign, 20 and above suspicious, 65 and above malicious but only with two independent categories or a critical rule.
If he pushes on "why not add them up": because three weak findings would then reach 100 and scream malicious, and the score could exceed any meaning.
Why doesn't a single 90-severity finding make the session malicious?
It can — severity 90 at confidence 0.8 is a "critical rule" and it is allowed to cross into malicious alone. Below that, a high score from one channel stays suspicious, because one suspicious behaviour is a lead and two independent ones are a story. The explanation printed with the verdict says exactly which case applied.

C. Code-level: "what does this file do?"

Point at ProcessScopeTracker.cs. What is it?
It decides whether an event belongs to the monitored tree. It keeps a map of pid to scope state — root, confirmed, unconfirmed, excluded — updated on every process-start event from the kernel's parent link. For non-start events it looks the pid up. Unconfirmed means "attributed by location", which is weaker evidence, and it is carried on the event as a field so nothing downstream can treat it as confirmed.
Why does PathKey exist?
Because two spellings of the same file must compare equal. It canonicalises and case-folds the path, and provides "directory name" and "is under" helpers. Both the sensitive-path catalog and the correlated rule X-002 use it — X-002 matches the file written into Startup to the file later executed by canonical path, not by file name, so a same-named program elsewhere cannot correlate.
What is Observability in BehaviorEvent?
How directly the sensor saw the fact: Direct from an OS event, Partial when attribution or completeness is limited, Inferred when it was deduced — the injected-process footprint, or a registry write whose key was resolved through a kernel object pointer — and Aggregated for rollups. It is a required field, and the dashboard renders it on every row, because the project's sixth requirement is that observed and inferred evidence are never blurred.
What is RuleFinding.Counterfactual?
The exact behaviour that would have stopped the rule firing. For F-002 it is "a read or a delete, or a write to a key Windows does not execute at sign-in". It is mandatory in the contract, so a rule cannot be written without stating where its own boundary is. It appears in the dashboard and in the exported report.
What does DetectionAggregator do?
It collapses repeated rule hits into one detection per rule and process inside a merge window — so a looping program produces one card with a count instead of thousands — and it escalates the card when a new evidence channel joins. It also appends the event sequence numbers, which is what makes the evidence chain clickable.
What does VolumeGovernor do?
It watches the event rate. Above a threshold it starts sampling reads and marks the session as throttled, and that fact is carried into the counters and into the report as "counts are a sample under pressure". It counts only in-scope events — before I fixed that, machine-wide noise marked clean sessions incomplete.
What is in the SQLite database?
Four tables plus a full-text index: events, detections, processes and score samples. The events table is what the Files, Network, Timeline and Search screens read; the raw events are also appended to a JSONL file, which is both the evidence of record and the source for the replay fixtures.
How does the dashboard get live data?
Server-sent events. The client asks for a single-use ticket with its bearer token, then opens the stream with that ticket in the URL — so the token itself never appears in a URL, the address bar or a log. The stream sends a state frame, a stats frame, event batches, detections and score updates, plus a gap frame when something was lost.
Why does the agent serve the web app instead of a dev proxy?
Same origin. The bearer token and the host/origin guard then work with no CORS and no Origin rewriting — and the proxy setup I had first produced exactly those two bugs: a rewritten Host header and a 403 on the ticket POST.

D. Harder / design questions

How do you know a binary is unsigned? Prove it.
Three-way status: valid, invalid, or unknown, and unknown is never treated as unsigned. Two obvious implementations are wrong and I measured both. X509Certificate.CreateFromSignedFile only reads an embedded certificate, so it called a copy of whoami.exe unsigned while Get-AuthenticodeSignature said valid by catalog. WinVerifyTrust returns TRUST_E_NOSIGNATURE for catalog-signed files — the same code as no signature at all. So the shipped path builds the Authenticode chain explicitly and returns Unknown when it cannot decide.
This answer is the best proof in the project that the work was measured rather than assumed.
Can you detect file deletion?
No — and I know that from measurement, not from documentation: 26 live deletions produced zero file events, while a directory removal does surface. So F-006, which is the ransomware-shaped rule, keys on rewrites and marker-appending renames instead of pretending deletions are visible. The report's observability table states it.
How would you detect process injection?
Not directly with the providers I use — the kernel provider here has no thread-injection keyword. So P-008 detects its footprint instead: a process in the application's directory whose creator was never observed, which is what cross-process creation leaves in the process table. It is labelled Inferred, not Direct.
What if the program does nothing suspicious for ten minutes and then acts?
The score decays with a half-life of 15 minutes but has a floor of 0.6, so early evidence fades rather than disappearing while the session is open; new behaviour pushes it back up immediately, and the peak score is recorded separately so the report shows the highest point even if risk has fallen since.
Two copies of the same weak signal — do they double the score?
No. Repeats are merged by the aggregator into one detection with a count, and even separate detections combine with noisy-OR, so ten copies of a 0.2-weight signal approach 0.2, they never reach 1. Confidence does rise with a repeat count, which is why the merge is not just cosmetic.
How do you test something that needs Windows kernel events?
Three levels. Unit tests for everything pure — scope tracking, scoring, path keys, every rule. Recorded scenarios: 54 JSONL fixtures replayed through the real pipeline with asserted rules, absent rules, band and score range, so a rule change that fires on a benign twin fails. And live probes: I run a real session, capture the JSON the agent serves, and use that capture as the dashboard's fixture, so the UI tests cannot pass while a DTO breaks the page.
What did you get wrong, and how did you find out?
Several, all written up. A session that ran only echo hello collected 104 bogus registry deletes because I was mapping the kernel's cache traffic by substring. Every System32 binary open was reported as a write until I read the create disposition. The first version of P-001 and P-002 made every shell fixture report two findings, so I made them disjoint by construction. And a metadata retry I added for short-lived processes made results worse — 9 of 24 resolved instead of 13 — because between attempts the process is more dead and the sleep blocked the dispatch thread; I reverted it and wrote down the measurement.
Having a "what I got wrong" answer ready is usually the difference between a good and a great viva.
What would you do next?
Two things, in order. The plan's phase five is a full end-to-end run on a clean Windows VM with a documented demo script, then a limitations document. After that, an advisory machine-learning layer that is displayed beside the rule score and never changes the verdict until it is calibrated — because a model that cannot explain itself would undo the main property of the project.

The five-minute demo

  1. bash scripts/verify.sh — all tests, the catalogue gate, 54/54 scenarios. This is the cheapest proof; show it first.
  2. Run the desktop app, or dotnet run --project src/Argus.Agent -- --web-root web/dist and open the printed URL. Point out that the agent serves the dashboard (same origin).
  3. Click Monitor an application, type C:\Windows\System32\notepad.exe, then Check this file: show the signature check and SHA-256 preview before anything starts.
  4. Start monitoring. On Live: counters, coverage "complete", flat risk chart, harmless signal feed. Say "Benign 0.0 means no significant observed indicators, not proof of safety".
  5. If you want a detection live, launch cmd.exe as the target with arguments /c reg add HKCU\Software\Microsoft\Windows\CurrentVersion\Run /v Demo /d C:\Windows\System32\notepad.exe /f.   7. Click HTML in the header: the exported report opens from file:// with summary, detections, evidence, collection health, the observability table, limitations and the embedded JSON.
